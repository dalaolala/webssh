## 一、基础代码质量与技术债 (Code Review)

### 🔴 确认 Bug（可能引发运行时崩溃）

#### Bug 1：`handleUploadDone` 调用了未导入的函数
- **文件**：`frontend/src/components/QuickSftpFileManager.vue`
- **位置**：`handleUploadDone()` 函数体
```js
// 调用了 clearCompletedTasks，但 useSftpUpload 解构中实际导入的是 clearAllFinishedTasks
const handleUploadDone = () => {
  clearCompletedTasks(); // ❌ ReferenceError！此函数未从 composable 解构
  refreshDirectory();
};
```
- **影响**：点击"完成并刷新"时必定抛出 `ReferenceError`，上传结束后无法正常清理任务列表。
- **修复**：将 `clearCompletedTasks()` 改为 `clearAllFinishedTasks()`。

---

#### Bug 2：HTTP 上传进度事件静默失效
- **文件**：`backend/routes/sftp-quick-simple.js` · 上传路由 `POST /upload`
- **问题**：代码中引用 `global.ioInstance` 来广播进度事件，但 `backend/server.js` 中从未赋值 `global.ioInstance = io`，导致该变量始终为 `undefined`，进度回调永远不会触发。
- **影响**：HTTP 多部分上传（非 Electron Socket 路径）完全没有进度反馈。
- **修复**：在 `server.js` 初始化时添加 `global.ioInstance = io`，或将 `io` 实例通过参数注入 router。

---

#### Bug 3：`sftp.js` 中的超时定时器污染后续连接
- **文件**：`backend/routes/sftp.js` · `getSftpConnection()`
- **问题**：每次建立连接时设置一个 10 分钟的 `setTimeout`，但手动断开后 `sftpConnections.delete(key)` 已执行；若用户在这 10 分钟内重新连接，Map 中已存入新连接对象，旧定时器触发时会把新连接关掉：

```js
setTimeout(() => {
  if (sftpConnections.has(key)) {
    sftpConnections.get(key).disconnect(); // ❌ 可能 disconnect 的是新建的连接
    sftpConnections.delete(key);
  }
}, 10 * 60 * 1000);
```

- **修复**：维护一个 `timers` Map，重连时先 `clearTimeout` 再设新定时器。

### 🟡 设计缺陷（不崩溃但存在隐患）

#### 缺陷 1：`confirmedOverwrites` Set 无限增长（内存泄漏）
- **文件**：`backend/socket/socketHandler.js`
- **位置**：模块顶部 `const confirmedOverwrites = new Set()`
- **问题**：每次用户确认覆盖文件时，`remotePath` 被 `add` 进集合，虽然上传完成后有 `delete`，但若上传在确认后失败，`delete` 不会执行，该路径永久驻留。长时间运行后 Set 体积不断膨胀。同理，`uploadResumables` Map 的清理也仅在上传成功时触发，失败时残留。

---

#### 缺陷 2：`terminal.js` Store 是孤立的死代码
- **文件**：`frontend/src/stores/terminal.js`
- **问题**：该 Pinia Store 定义了完整的 SSH Socket 连接逻辑，但当前项目中 `QuickConnectTerminal.vue` 直接在组件内管理 `socket`，完全没有使用这个 Store。Store 中还保留着 `terminalOutput` 字符串拼接逻辑（`terminalOutput.value += output`），这是旧架构遗留物，与现在基于 xterm.js 的架构不兼容。
- **建议**：删除 `stores/terminal.js` 或归档，避免新人误用。

---

#### 缺陷 3：`filterNode` 逻辑判断字段不一致
- **文件**：`frontend/src/views/QuickConnect.vue`
- **位置**：`filterNode()` 函数

```js
const filterNode = (value, data) => {
  if (!value) return true
  if (data.type === 'group') return true // ❌ treeData 中分组节点没有 type 字段
  // 实际分组节点使用 data.isLeaf === false 来标识
}
```

- **影响**：搜索时分组节点的条件判断永远为 `false`，依赖 Element Plus Tree 内部的子节点匹配逻辑，行为非自定义意图，可能导致分组在某些过滤条件下意外隐藏。

---

#### 缺陷 4：`useSftpUpload` 每次挂载创建独立 Socket 连接
- **文件**：`frontend/src/composables/useSftpUpload.js`
- **问题**：`initSocket()` 内调用 `io()` 会建立一条**新的** Socket.IO 连接，与 `QuickConnectTerminal.vue` 中的 SSH 连接完全独立。这意味着在"终端 + 文件管理器"场景下，同一个页面建立了**两条** WebSocket 连接到同一个后端。
- **建议**：复用同一个 Socket 实例（通过 provide/inject 或 Singleton 模块导出），减少连接数。

---

#### 缺陷 5：大文件内容编辑无 Size Guard
- **文件**：`backend/utils/sftpHandler.js` · `getFileContent()`
- **问题**：`sftp.readFile(filePath, 'utf8', ...)` 会将整个文件内容加载到内存返回给前端，对于大文件（如几百 MB 的日志）会造成 OOM。前端 Monaco Editor 接收到后渲染也会导致浏览器卡死。
- **建议**：增加文件大小检查，超过（如）2MB 时拒绝编辑或仅加载头部 N 行。

---

### 🟢 代码规范问题

- **`sftp-quick-simple.js`**：`process.on('SIGINT'/'SIGTERM'/'beforeExit')` 在路由模块中注册进程级别的事件，是不良实践。应在 `server.js` 统一管理。
- **`QuickConnect.vue`**：单文件 900+ 行，`<script setup>` 中混杂了历史管理、加密导入导出、WebDAV、表单校验、路由跳转等逻辑，建议抽取为若干独立 Composable（`useConnectionHistory`、`useExportImport` 等）。
- **`crypto.js (backend)`**：同步使用 `node-forge` 生成 2048-bit RSA 密钥对，此操作耗时可达 200-500ms，会**阻塞 Node.js 事件循环**（`forge.pki.rsa.generateKeyPair` 是同步 API）。建议改用 Node 原生 `crypto.generateKeyPair` 的异步形式或在进程启动前提前完成。

## 二、核心功能边界完善 (Edge Cases)

### 2.1 SSH 终端

| 场景 | 当前状态 | 风险 |
|------|----------|------|
| 网络中断后自动重连 | ❌ 仅提供手动"重连"按钮 | 用户可能不知道已断线，仍在输入命令 |
| 重连后终端内容恢复 | ❌ 重连后 xterm 完全清空 | 历史输出丢失 |
| `keepaliveInterval=30s` 但无 keepalive 失败处理 | ⚠️ ssh2 的 keepalive 失败时会触发 `error` 事件，当前已捕获，但仅发送 `ssh-closed` 到前端，没有自动重连 | 空闲会话静默断开 |
| 终端窗口大小变更节流 | ⚠️ `handleResize` 中有 `resizeTimer` 防抖，但 `QuickConnectTerminal` 里没有对 `sftp-sidebar` 展开/收起做足够的 resize 触发 | SFTP 侧栏切换后终端列数不准确 |
| 粘贴含行尾空格的内容 | ⚠️ `trimLineTrailingSpaces` 会破坏含结尾空格的命令（如 `echo "hello "`) | 命令执行结果与预期不符 |
| `space` 键被覆盖 | 🔴 `attachCustomKeyEventHandler` 中对 Space 键 `preventDefault + emit` 会导致 xterm 内置输入行为与自定义路径并存，在 IME 输入法激活时可能重复发送空格 | 中文输入时空格选词异常 |

### 2.2 SFTP 文件管理

| 场景 | 当前状态 | 风险 |
|------|----------|------|
| 浏览器环境（非 Electron）拖拽上传 | ❌ `file.path` 在浏览器中为 `undefined`，回退为 `file.name`，后端 `fs.existsSync(localPath)` 检查 `file.name` 必然失败 | Web 版拖拽/点击上传完全无法工作 |
| 删除非空目录 | ❌ `sftpHandler.deleteDirectory` 使用 `sftp.rmdir`，仅删除空目录，非空目录报错 | 用户无法删除含文件的文件夹 |
| 下载大文件 | ⚠️ `downloadFile` 使用 `fastGet` 先将远程文件完整下载到本地 `temp/` 目录，再 `pipe` 给 HTTP Response，双倍磁盘占用 | 1GB 文件需要 1GB 临时空间 |
| SFTP 会话刷新页面后失效 | ❌ `sessionId` 仅在内存中，刷新后 sessionId 丢失，SFTP 连接无法复用 | 无感知的用户动作导致会话断开 |
| 心跳失败时前端无感知 | ⚠️ `sendHeartbeat` 失败只打 `console.warn`，前端 `isConnected` 仍为 `true`，实际服务端 session 可能已超时 | 用户继续操作触发"会话不存在"错误，体验差 |
| 多标签页 SFTP 并发上传事件交叉 | ❌ `useSftpUpload` 的 Socket 连接全部监听相同事件名，多 SFTP 页面并发时可能交叉接收对方的进度事件（靠 `uploadId` 匹配，但 `localPath` 匹配作为 fallback 不安全） | 进度显示错乱 |

## 三、性能与安全性诊断 (Performance & Security)

### 3.1 安全风险

#### 🔴 高危：WebDAV 凭据明文传输与明文存储
- **文件**：`frontend/src/components/WebdavSync.vue`（配置）→ `backend/routes/webdav.js`
- **问题**：WebDAV 的 `url/username/password` 由前端 `localStorage` 保存，通过 HTTP POST 明文传给后端转发，后端不做任何加密。这与 SFTP 连接时精心设计的 RSA+AES 混合加密形成鲜明对比。
- **建议**：WebDAV 凭据同样走加密通道，或直接从前端发起 CORS 请求（绕开后端中转）。

---

#### 🔴 高危：SFTP 文件下载存在路径穿越风险
- **文件**：`backend/routes/sftp-quick-simple.js` · `GET /download`
- **问题**：

```js
// remotePath 来自用户 Query 参数，未经净化直接传入 SFTP 操作
await sftpHandler.downloadFile(remotePath, tempFilePath);
// tempFilePath 的文件名通过 path.basename(remotePath) 计算
tempFilePath = path.join(tempDir, `download_${Date.now()}_${path.basename(remotePath)}`);
```

- 恶意 `remotePath`（如 `../../../../etc/shadow`）可能使远程服务器上的敏感文件被下载并发送到前端；`path.basename` 虽保证了本地临时文件名安全，但远程读取路径完全未受控。
- **建议**：对 `remotePath` 进行规范化检查，校验必须以当前工作目录为前缀。

---

#### 🟡 中危：`io.emit` 广播上传进度给所有连接客户端
- **文件**：`backend/routes/sftp-quick-simple.js` · `POST /upload`（虽然 `global.ioInstance` 目前未赋值）
- **问题**：代码意图是 `io.emit('sftp-upload-progress', ...)` 广播到**所有**连接的 Socket 客户端，而不是仅发给上传发起者。如果修复了 Bug 2，在多用户（或多标签）场景下会导致进度信息泄露。
- **建议**：改为 `socket.emit` 定向发送，或通过 `room/namespace` 隔离。

---

#### 🟡 中危：RSA 私钥存在内存中，无进程间保护
- **文件**：`backend/utils/crypto.js`
- **问题**：`keyPair` 存储在模块作用域中，Node.js 进程崩溃转储（core dump）或内存扫描可读取私钥。在 Electron 环境中，私钥在应用生命周期全程暴露在内存。
- **说明**：对于桌面工具可接受，但建议添加注释说明这是设计决策而非疏忽。

---

### 3.2 性能瓶颈

| 问题 | 位置 | 量化影响 |
|------|------|---------|
| RSA 密钥对生成同步阻塞事件循环 | `backend/utils/crypto.js` `initKeyPair()` | 首次请求延迟 200-500ms，期间其他请求被阻塞 |
| 两条并发 Socket 连接 | `useSftpUpload.js` + `QuickConnectTerminal.vue` | 每个终端+SFTP 场景多一条 WebSocket 连接 |
| `treeData` computed 每次重建 Groups 对象 | `QuickConnect.vue` | 100 条历史记录时，每次 `historyList` 变化都完整重建树，O(n) |
| HTTP 上传走磁盘中转 | `sftp-quick-simple.js` `/upload` | 文件先 multer 写磁盘 → SFTP 再读磁盘上传，双 I/O |
| xterm 缓冲区清理使用 scrollback hack | `XtermTerminal.vue` `cleanupBuffer()` | 临时调低 `scrollback` 会触发 xterm 内部重渲染，可能闪烁 |
| Monaco Editor 初始加载 | `QuickSftpFileManager.vue` | ~2-4MB JS 打包体积，首次打开文件编辑器时阻塞 |

### 🚀 P1 - 高优 Quick Win（1-2 天可完成，用户体验飞跃）

#### 功能 1：SSH 终端断线自动检测 + 视觉提示
- **价值**：当前断线无感知，用户可能继续输入却无响应，困惑度极高。
- **方案**：监听 `socket.on('ssh-closed')` / `socket.on('disconnect')` 时，在 xterm 中输出高亮警告行，并在底部状态栏显示「已断线 · 点击重连」的 CTA，取代现有的静默断线。
- **工作量**：前端改动 ~30 行，无后端改动。

#### 功能 2：SFTP 心跳失败时前端感知与自动断开
- **价值**：心跳失败后操作必然报错，用户不知所措。
- **方案**：`sendHeartbeat` 连续失败 2 次后，自动调用 `disconnectSftp()`，将 `isConnected` 置为 `false`，并展示"SFTP 会话已超时，请重新连接"的 Banner，同时提供一键重连按钮。
- **工作量**：`useQuickSftp.js` 改动 ~20 行。

#### 功能 3：终端多标签快捷键
- **价值**：对运维人员高频操作，极大提升效率。  
- **方案**：在 `QuickConnectLayout.vue` 的 `window.addEventListener('keydown')` 中拦截：
  - `Ctrl+T` → `createNewTab()`  
  - `Ctrl+W` → `closeTab(activeTabId)`  
  - `Ctrl+1~9` → 切换到第 N 个标签  
- **工作量**：前端改动 ~25 行，零后端改动。

#### 功能 4：SFTP 文件列表过滤搜索
- **价值**：在目录文件众多时快速定位，类似 IDE 文件树过滤。
- **方案**：工具栏增加一个原生 `<input>` 搜索框，本地过滤 `files` computed 数组（`file.name.includes(keyword)`），零额外 HTTP 请求。
- **工作量**：`QuickSftpFileManager.vue` 改动 ~40 行，零后端改动。

### 🔧 P2 - 中优（3-5 天，完善核心功能）

#### 功能 5：非空目录递归删除支持
- **价值**：当前删除目录若非空则报错，用户体验差，是 SFTP 功能的明显缺失。
- **方案**：在 `sftpHandler.js` 新增 `deleteDirectoryRecursive(path)` 方法：先 `readdir` 列出子项，逐一递归删除文件/子目录，最后 `rmdir` 自身。前端删除目录时提示"此目录包含 X 个文件，确认递归删除？"。
- **工作量**：后端 ~50 行，前端 ~10 行。

#### 功能 6：主机列表书签 / 快速收藏置顶
- **价值**：历史记录最多 100 条，常用服务器被新记录顶走。置顶/收藏可解决此痛点，契合极简理念。
- **方案**：历史记录 JSON 增加 `pinned: boolean` 字段，树形数据中收藏夹为固定分组"⭐ 收藏"。右键菜单增加"收藏/取消收藏"选项。纯前端实现，零后端改动。
- **工作量**：前端改动 ~60 行。

#### 功能 7：文件下载进度条（流式下载）
- **价值**：大文件下载目前无任何反馈，浏览器表现为长时间无响应。
- **方案**：后端改为设置 `Content-Length` 响应头（先用 `stat` 获取文件大小），前端使用 `fetch` + `ReadableStream` 实现带进度的下载，通过 xterm 状态栏或 SFTP 进度区展示百分比。
- **工作量**：后端改动 ~20 行，前端改动 ~50 行。
